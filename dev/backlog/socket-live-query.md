## Условия, зафиксированные при обсуждении шардинга (2026-07-29)

Будущий рецепт: изменения сущностей в БД пушатся всем, у кого в квери-клиенте
есть их айдишники; человек состоит во множестве быстро меняющихся комнат.
Шардинг для этого профиля — не угроза, а необходимость (без него каждый узел
парсит весь поток изменений БД). Дребезг подписок гасится линжером и
объединением: нода подписывается на первого локального зрителя комнаты. Но
рецепт обязан соблюсти эти условия:

- **Комнаты — точные `{model, id}`**: НИКАКИХ `keys` в идентичности комнаты
  (размножение комнат × варианты ключей, издатель публикует во все) и НИКАКИХ
  `$room`-матчеров для адресации (матчеры едут по общему каналу — весь
  live-query-трафик вернётся на него, шардинг обнулится). Изменившиеся ключи — в
  payload сообщения, клиент фильтрует у себя.
- **Спейс live-query — `resumable: false`** (опт-аут спейса — РЕАЛИЗОВАН): его
  комнаты не пишутся в conn-паспорт (иначе сквозная запись комнат молотит Redis
  на каждый скролл) и не восстанавливаются resume'ом — клиент ре-джойнит из
  своего состояния (комнаты и так выводятся из кеша квери).
- **Redis-специфика в доке-рецепте бекплейна**: в кластерном Redis обычный
  pub/sub рассылается на весь кластер независимо от подписок — нужен sharded
  pub/sub (`SSUBSCRIBE`, Redis 7+) либо одиночный pub/sub-узел.
- **`maxRooms`** для такого канала поднимается (сотни комнат на соединение).
- **Батч-джойн** (несколько комнат одним кадром) — будущая оптимизация протокола
  под этот профиль: сейчас каждый вход — отдельный кадр.
- Заметка рецепту (не транспорту): joiner бежит на каждый вход — проверка прав
  на каждую сущность при скролле дорога; рецепту нужен дешёвый joiner (право уже
  проверила квери, отдавшая сущность).
