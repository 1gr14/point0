> **СОСТОЯНИЕ.** Не начато; вынесено из волны 3 сокетов как отдельная тема
> (2026-07-17). Ниже — проверенные факты, план и открытые решения.

## Факты (проверено экспериментом в конце волны 3)

- Элемент в connect `data` СЕГОДНЯ НЕ проезжает: фикстурный тест (JSX в `data`
  коннектора) валит сам коннект — канальная ветка fetcher.ts сериализует
  `connectOutput` целиком СВОИМ `transformer.stringify`, ДО какой-либо
  RSC-нормализации (executor'ный `normalizeRscOutput` этот путь не проходит;
  обычные лоадеры HTTP-эндпоинтов через него проходят — поэтому у кверей/страниц
  элементы в данных работают).
- Сокетные пути (пуш-input, реплаи хэндлеров, чанки стрим-reply) и NDJSON/SSE
  yield'ы подписок ходят через сырой `_getTransformer` С ОБЕИХ СТОРОН — элементы
  не кодируются вовсе.
- Направление защищено и должно остаться таким: инпут ВСЕГДА парсится сырым
  трансформером — правило из point0.ts: «the server never decodes React elements
  from untrusted bytes». Клиент→сервер элементы не поедут никогда.

## План (черновой — нормализация полная, решено предварительно)

Сергей: «гнать через полный `normalizeRscOutput` с `.rsc({ depth })` было бы
логично». Проблема не концептуальная, а объёмная — что именно придётся сделать:

- [ ] **Connect data**: прогнать `channelConnectorOutput.data` через
      `normalizeRscOutput` (опции `.rsc` канала) перед сериализацией ответа в
      канальной ветке fetcher.ts; клиентский `_fetchChannelConnect` уже парсит
      через `_getTransformerWithRsc` (стандартный endpoint-путь) — тут скорее
      всего только серверная половина.
- [ ] **Сервер→клиент по сокету** (пуш-input в `sendToClient`, reply
      `serverReply`): нормализация КАЖДОГО payload'а по `.rsc`-опциям поинта +
      сериализация RSC-обёрнутым трансформером; клиентский парс этих же точек
      (dispatch, reply) — через `_getTransformerWithRsc`. (Стрим-реплаи и
      `replyChunk` выпилены 2026-07-25 — стриминг теперь обычные пуши
      clientHandler'а, потребляемые `iterateMessagesFromServer` / листенерами,
      это тот же пуш-input.)
- [ ] **Yield'ы подписок**: нормализация каждого `{v}` на сервере
      (subscription-stream) + RSC-парс конвертов на клиенте. Клиентский дуck
      subscription.ts придётся расщепить: inputKey остаётся на сыром
      трансформере (идентичность), конверты — на RSC-обёрнутом.
- [ ] **Тесты**: элемент в connect data / пуше / реплае / стрим-чанке / yield'е
      — e2e с реальным рендером (isValidElement + типы/пропсы), плюс негативные:
      клиент→сервер маркеры НЕ распарсиваются.

## Открытые решения (обсудить до старта)

- **Ленивые component-refs в пушах.** Элемент может ссылаться на
  component-point; на HTTP-пути клиент резолвит ссылку из манифеста
  (слот-враппер даёт чанку догрузиться). Пуш приходит в произвольный момент —
  чанк компонента может быть не загружен; проверить, что слот-враппер-механика
  переносится на сокетный парс как есть, или пуш должен ждать догрузки
  (аналогично предзагрузке хэндлеров при коннекте?).
- **`defer()`-дырки.** У HTTP-ответов дырки едут отдельным NDJSON-стримом; у
  сокетного сообщения такого транспорта нет. Вариант v1: `defer()` в сокетных
  payload'ах — тайп/рантайм-ошибка (нормализация без дырок).
- **Объём v1**: всё сразу или сначала connect data + подписки (HTTP-шные,
  дешевле), сокетные пуши — вторым шагом.
- **`attempt`/бюджет глубины**: `.rsc({ depth })` читается с какого поинта —
  хэндлера или родительского канала (у подписок — самого поинта; у хэндлеров
  своего `.rsc` в чейне нет — решить, наследовать ли канальный).
